# Documentation gaps found via git history

This is a retrospective, mined from the full commit history (93 commits, 41
release tags, 2026-07-05 through 2026-07-26) and the three files this repo
actually keeps in `docs/`: [`SCHEMA_VERSIONS.md`](SCHEMA_VERSIONS.md) (a
generated version/source-URL table), and the two feature plans,
[`mcp-prompts-workflow-plan.md`](mcp-prompts-workflow-plan.md) and
[`mcp-workflows-expansion-plan.md`](mcp-workflows-expansion-plan.md). This
repo does **not** have a full PRD/architecture doc set — no separate
requirements, architecture, or design doc exists outside those three files
and the README. That narrows *which* local docs each gap below is compared
against, but it doesn't change the thoroughness of the git-log mining
itself: every `fix:` commit implying a design/doc gap and every `feat:`
commit retrofitting something that should have been anticipated is covered
below, across all 41 releases.

This repo is generated by a separate tool, **mcpify**
(`/Users/lucianoguerche/Documents/GitHub/mcpify`, not modified as part of
this exercise). Many `fix:` commits here turn out to be downstream patches
for bugs that live in mcpify's shared Rust code-generation templates —
logging setup, the config cascade, embedded-store path resolution,
CI/release workflow shape, credential handling, TLS setup — anything
plausibly identical across every mcpify-generated MCP server, not specific
to the Bitbucket Data Center API. Those are tagged **(shared mcpify-template
gap)** below; several are explicitly confirmed in the commit messages
themselves to also exist in sibling repos (`spotify-mcp-rs`,
`bamboo-mcp-rs`) or to have been fixed upstream in mcpify's own `.tera`
templates. Fixes tied to something genuine about the Bitbucket Data Center
API itself (its auth surface, its `operationId`/spec drift across versions,
its catalog's domain shape) are tagged **(repo-specific)**.

**Every entry below tagged `(shared mcpify-template gap)` has been
cross-checked against mcpify's own planning docs**
(`mcpify/docs/product-brief.md`, `prd.md`, `architecture.md`) and its own
retrospective, `mcpify/docs/DOC-GAPS.md`, plus `mcpify/CHANGELOG.md` for the
corresponding upstream fix. Where mcpify's own `docs/DOC-GAPS.md` already
has an entry covering the same root cause, this file points to it by name
instead of re-deriving a differently-worded version — the two files are
meant to be read together, not duplicated. Where a shared-tagged entry here
has **no** counterpart in mcpify's own retrospective, that's flagged
explicitly as a new finding worth a fresh entry there — this turned out to
be true for roughly two-thirds of the shared-tagged entries below, which is
itself a signal (see the new Lessons item on this).

## Lessons for future docs

Distilled from the recurring failure patterns below — write these into the
*first* planning doc for a new mcpify-generated project, not discovered one
bug at a time. mcpify's own `docs/DOC-GAPS.md` has its own 7-item "Lessons"
list, derived from the same kind of git-history mining applied to mcpify
itself rather than to one generated project; items 1-4 below are this
repo's evidence for lessons mcpify's list *already* captures, restated with
this repo's specifics. Items 5-8 are patterns this repo's history surfaces
that mcpify's own list does not yet capture.

### Confirms mcpify's existing lessons

1. **Specify transport-mode-aware behavior for anything touching stdout —
   don't just say "log to stderr."** Directly confirms mcpify's own Lesson
   1 ("Specify transport/mode-aware behavior explicitly for anything
   touching shared OS resources"). This repo's v0.2.7 fix (logs
   unconditionally to stderr) is the *first-order* fix mcpify's own
   `docs/DOC-GAPS.md` "stdio vs HTTP logging stream" entry describes as
   "directionally correct for stdio mode but wrong for http mode" — i.e.
   even the fix this repo shipped and mcpify upstreamed (mcpify v0.5.10) was
   itself an incomplete reading of the requirement, only corrected
   transport-conditionally in mcpify's 2026-08-01 follow-up (after this
   repo's own history ends). One doc gap produced two rounds of fixing.

2. **Any doc describing an embedded-asset pattern (SQLite stores, compiled
   schemas, model weights) must cover its full lifecycle up front.**
   Directly confirms mcpify's own Lessons 2 ("no CWD-relative filesystem
   paths") and 5 ("concurrency and platform-specific I/O semantics belong
   in the architecture doc"). This repo alone produced 8+ separate fix
   commits against this one gap (path resolution: v0.2.1/v0.2.2;
   concurrency: v0.4.3, v0.5.3, v0.5.8, v0.7.2; size budget: v0.2.5, v0.4.1)
   — a real-world multiplier on top of the "6 separate fix commits, v0.5.4
   through v0.10.1" mcpify's own Lesson 2 already tallies just from its own
   generator-repo history, before counting what it caused downstream in
   every generated project.

3. **A doc that says "generated code — do not hand-edit" must also specify
   the accepted pattern for hand-authored extensions that need to survive
   the next regeneration.** This is *not* explicitly one of mcpify's 7
   existing lessons — the closest is Lesson 6 ("track cross-repo
   propagation"), which is about a different problem (redundant
   re-diagnosis, not extension-survival). See the new "MCP prompts" finding
   below (v0.6.0) — this deserves promotion to its own lesson in mcpify's
   list, not just a mention here.

4. **CI/release pipeline docs should specify defaults, not let each repo
   discover the gap independently:** `timeout-minutes` on every job (missing
   here until v0.7.3), target-platform decisions tied to native dependencies
   resolved *before* the first release (v0.2.14's ONNX/`ort` matrix
   breakage), and multi-arch container image strategy decided deliberately
   (v0.7.6's QEMU-first, v0.7.7's native-runner correction). The multi-arch
   half of this directly confirms mcpify's own "multi-arch container images
   not specified" `docs/DOC-GAPS.md` entry — mcpify hit and fixed the
   *identical* QEMU-then-native-runner sequence in its own templates
   (v0.11.12 → v0.11.14) at the same time this repo did downstream. The
   `timeout-minutes` half has no mcpify `docs/DOC-GAPS.md` counterpart at
   all (see the new finding at v0.7.3 below) despite mcpify fixing the same
   gap in its own CI and in its Rust templates within days of this repo.

### Not yet in mcpify's own lessons list

5. **"Generated code, do not hand-edit" needs an escape hatch, and it needs
   one before the first hand-authored capability ships, not after.**
   `architecture.md` §5's "version-aware regions" is the *only* existing
   mcpify doc describing safe hand-adjacent editing, and it's scoped
   narrowly to small pure-data marker regions (a label→file map, a list of
   choices) — nothing in mcpify's docs addresses a whole new hand-authored
   *capability* (this repo's MCP prompts feature: 12 new files, ~800 lines,
   a naming convention invented from scratch) that must coexist with
   `force: true` regeneration. Every mcpify-generated repo that wants to add
   something mcpify's generator doesn't yet produce will hit this exact
   open question.

6. **A "self-contained by design" decision needs its cost budget attached to
   *every* instance of the pattern, not just the one that got measured
   first.** mcpify's own Lesson 4 already says this, but its own worked
   example (schema `$ref` duplication, ~115 MB) is a *different* instance of
   the same underlying decision (REQ-2.4.1's "single self-contained
   artifact") than the one that bit this repo twice (v0.2.5, v0.4.1: the
   *store DB itself* growing past crates.io's 10 MiB limit as embeddings and
   version count grew). Both are downstream of the same one-line PRD
   decision with no attached budget — mcpify's Lesson 4 should cite both,
   not just the schema-duplication case it currently references.

7. **"Populate every version's data, not just the default's" needs to be a
   stated invariant, not something each new backfill script has to
   remember.** This repo hit "some derived per-version artifact only ever
   gets populated for the default version" *twice*, for two different
   artifacts: embeddings (v0.2.3/v0.2.4, recurring at v0.4.0 for a version
   added *after* the first fix existed) and, less severely, Docker's store
   `COPY` list (v0.2.14). The common shape — multi-version support was
   retrofitted (`architecture.md` §5) onto a design that originally assumed
   one store — needs one explicit "everything that touches
   `mcp_store*.db` must iterate the full version ledger, not just the
   default" rule, not three independent rediscoveries per repo.

8. **README ownership (generator-owned vs. hand-maintained) needs to be
   stated, in both directions.** This repo's README fell behind the actual
   CLI surface early (v0.2.12, before any template sync had even happened —
   likely inherited thinness in mcpify's own initial README template), and
   later a `mcpify sync` silently *dropped* hand-added README sections
   (v0.5.0) that existed only because an older template never generated
   them. Neither direction is addressed by any mcpify doc; `architecture.md`'s
   Folder Structure diagram lists `README.md` with no content specification
   at all.

## Dated entries

## 2026-07-26 — v0.7.6 / v0.7.7 — GHCR image was never actually multi-arch (shared mcpify-template gap)

### Doc gap
No doc (README's Docker section or a CI/release design doc) specified that
the published container image must support both `amd64` and `arm64`, or how
to build that reliably. The release workflow ran `docker/setup-buildx-action`
but never passed `platforms:` to `docker/build-push-action`, so it silently
built `amd64`-only images for a repo whose users plausibly include Apple
Silicon and arm64 CI runners.

**Already tracked in mcpify's own retrospective — see mcpify's
`docs/DOC-GAPS.md` entry "2026-07-26 - multi-arch container images not
specified (v0.11.12 - v0.11.14)."** That entry traces the same root cause to
`mcpify/docs/prd.md` REQ-2.3.7 ("Packaging & delivery"), which requires "a
CI/CD pipeline with automated versioning/publishing" but never states an
architecture-coverage requirement (amd64 **and** arm64) or flags that
QEMU-emulated cross-arch builds are unreliable in CI. mcpify's own generator
went through the *identical* two-step fix — QEMU first (mcpify v0.11.12,
2026-07-26), native runners second (mcpify v0.11.14, same day) — essentially
simultaneously with this repo's own v0.7.6/v0.7.7, since this repo's fixes
were applied by hand ahead of/alongside the matching template fix landing
upstream.

### Resulting work
Two follow-on releases: 0.7.6 added the missing `platforms:
linux/amd64,linux/arm64` plus QEMU emulation; 0.7.7 replaced QEMU (slow,
implicitly a stopgap) with a proper matrix build — native `linux/amd64` and
native `linux/arm64` (on an arm64 runner) built and pushed by digest, then
merged into one manifest via `docker buildx imagetools create`.

## 2026-07-26 — v0.7.5 — catalog schemas still not fully self-contained after the first $ref fix (shared mcpify-template gap)

### Doc gap
No doc specified the invariant "every stored operation schema must be fully
self-contained (all `$ref`s inlined, except genuine reference cycles)" —
this was fixed once already at v0.7.4 for `get`-tool response schemas
specifically, but the broader catalog (`mcp_store.db`,
`generated_schemas.json`) still carried a `$defs`-block indirection instead
of fully-inlined refs.

**Already tracked — see mcpify's `docs/DOC-GAPS.md` entry "2026-07-21 to
2026-07-26 - self-contained schema/`$ref` handling took three iterations
(v0.5.12, v0.11.5, v0.11.7)."** This is the third leg of that exact saga.
The entry traces the root cause to `mcpify/docs/v1-implementation-plan.md`'s
decision to embed a full standalone schema copy per operation — "simpler
and more robust than cross-schema `$ref` resolution, at the cost of some
file size" — a decision `prd.md` REQ-2.4.1 and `architecture.md` §2 ("Data
Layer") both praise as "self-contained" without ever specifying what
self-contained should mean at the `$ref`-inlining level. mcpify's matching
generator fix (fully inline instead of localize to `$defs`) landed as
v0.11.7 the same day as this repo's v0.7.5.

### Resulting work
Recursively inlined every non-cyclic `$ref` in the stored input/output
schemas, matching a companion fix landed in the mcpify generator itself.
Confirmed the only remaining `$ref`s are genuine cycles (e.g. `RestComment`
nesting itself for PR-comment reply chains), which have no finite
fully-inlined form.

## 2026-07-21 — v0.7.4 — generator's $ref expansion for get-tool responses was incomplete (shared mcpify-template gap, mcpify 0.11.5)

### Doc gap
No doc specified that a `get`-tool response's schema must be resolvable
without external context. A component `$ref` inside a get-tool response
could point at nothing in the returned snippet, silently producing
unusable schema output for callers who fetch operation details via `get`.

**Already tracked — see mcpify's `docs/DOC-GAPS.md` entry "2026-07-21 to
2026-07-26 - self-contained schema/`$ref` handling took three iterations."**
This is the second leg (the entry's v0.11.5 bullet: "Embed `$defs` into the
literal schemas the `get` tool returns, instead of leaving external `$ref`
pointers unresolved"). Same root cause as v0.7.5 above (REQ-2.4.1 / `v1
-implementation-plan.md`'s uncosted self-containment decision).

### Resulting work
Regenerated every configured API version's stores/schemas against the fixed
generator (`mcpify add-version --force`, mcpify 0.11.5), which now embeds a
`$defs` map alongside any `$ref` so responses are self-contained. Re-ran the
embeddings backfill for every refreshed store.

## 2026-07-21 — v0.7.3 — no default job timeout across CI/release workflows (shared mcpify-template gap)

### Doc gap
No CI/release design doc specified a default `timeout-minutes` for
generated workflow jobs. Without one, a hang falls back to GitHub Actions'
own 6-hour job ceiling instead of failing fast.

**Not yet in mcpify's own retrospective.** `mcpify/docs/DOC-GAPS.md` has no
entry for this, even though mcpify fixed the *identical* gap in its own CI
within days (`mcpify` v0.11.3, 2026-07-21: "Capped the release workflow's
build job at a 45-minute timeout"; v0.11.4, same day: "Capped mcpify's own
CI test job at a 20-minute timeout") — and confirmed by grep, the fix also
reached the generated-project templates themselves
(`mcpify/src/targets/rust/templates/.github/workflows/ci.yml.tera` and
`release.yml.tera` both now set `timeout-minutes`). The root cause traces to
`mcpify/docs/prd.md` REQ-2.3.7 ("Packaging & delivery"), which specifies a
CI/CD pipeline with automated publishing but never a default job-timeout
policy — the same gap the sibling `bamboo-mcp-rs` incident (a hung test
running until the 6-hour ceiling, referenced in this repo's own v0.7.2
commit message) demonstrates has real cost. This is a good candidate for a
fresh `mcpify/docs/DOC-GAPS.md` entry, since the fix already shipped
upstream but the retrospective doesn't mention it.

### Resulting work
Added explicit `timeout-minutes` to the release workflow's build job (45
min) and the CI workflow's test job (20 min). Directly motivated by a real
incident on a sibling repo (`bamboo-mcp-rs`): the mutex-poisoning bug below
turned one flaky test into a hang that ran until GitHub's own ceiling killed
it, because nothing in that repo's workflow bounded it any tighter.

## 2026-07-21 — v0.7.2 — shared store connection had no recovery path for a poisoned mutex (shared mcpify-template gap, confirmed in bamboo-mcp-rs)

### Doc gap
No doc specified the failure mode for the process-wide cached store
connection when a panic occurs while its lock is held. The generated
pattern propagated the poisoned-mutex error instead of recovering, so one
panic would permanently break every subsequent `search`/`get`/`call`/CLI
invocation sharing that connection for the rest of the process's life.

**Already tracked — see mcpify's `docs/DOC-GAPS.md` entry "2026-07-19 to
2026-07-26 - Windows-specific file-locking/timing semantics unaddressed for
the embedded store (v0.10.5 - v0.11.11)."** This exact fix is that entry's
v0.11.2 bullet ("The Rust target's generated server now recovers from mutex
poisoning on the shared `mcp_store.db` connection..."), dated the same day
as this repo's v0.7.2. The entry's stated root cause: `architecture.md` §2
("Data Layer") describes `mcp_store.db` extraction/embedding without ever
mentioning concurrency or platform-specific file-handle semantics.

### Resulting work
Explicitly confirmed as "the same bug found and fixed in bamboo-mcp-rs and
in mcpify's Rust code-generator template" — recovers from poisoning at every
lock site (safe here since all access is read-only) instead of propagating
it, and wraps the MCP protocol test in a 30s timeout so a future hang fails
fast rather than silently burning CI budget.

## 2026-07-20 — v0.7.1 — no established naming convention for hand-authored MCP-visible identifiers (repo-specific)

### Doc gap
`docs/mcp-prompts-workflow-plan.md` specified prompt *names* but never
established that MCP-visible identifiers should follow this ecosystem's
slash-command-style kebab-case convention rather than Rust's natural
snake_case — the plan shipped snake_case names
(`bitbucket_workflow_pull_requests`) that had to be renamed one release
later once the mismatch with client conventions became apparent.

This stays repo-specific: MCP prompts are not a mcpify-generated capability
at all (see the v0.6.0 entry below), so there is no generator template this
naming mistake could have inherited from or propagated to. It's a direct
downstream consequence of the v0.6.0 gap, though — a mcpify doc describing
the "hand-authored capability" pattern that gap identifies as missing
would plausibly also be the right place to pin down MCP-visible naming
conventions, so future hand-authored features (in this repo or any other)
don't make the same naming choice and have to redo it.

### Resulting work
Renamed every prompt identifier to kebab-case without the redundant
"workflow" segment (e.g. → `bitbucket-pull-requests`, master menu →
`bitbucket`), and updated every cross-reference (router descriptions,
content files, README table, tests) to match.

## 2026-07-20 — v0.6.0 — no documented pattern for hand-authored capability that must survive a future regen (shared mcpify-template gap)

### Doc gap
Every generated `.rs` file in this repo is headed "generated by mcpify. Do
not hand-edit," and `mcpify.yaml` sets `force: true` — but no doc anywhere
(mcpify's own docs, or this repo's) described the accepted pattern for
adding a genuinely hand-authored capability (MCP prompts, in this case) that
needs to coexist with, and survive, a future `mcpify sync`. This repo had to
invent the pattern itself: a dedicated `src/prompts/` module kept strictly
separate from generated `src/tools/`, markdown content pulled in via
`include_str!` rather than inline Rust literals, and an explicitly accepted
risk that a future regen could still overwrite the hand-edits.

**Not covered in mcpify's own docs at all — confirmed by direct search.**
Neither `mcpify/docs/prd.md` nor `mcpify/docs/architecture.md` mentions an
MCP "prompts" capability anywhere (every "prompt" hit in both files is
about *interactive CLI prompts* — PRD REQ-1.2.4's securitySchemes fallback,
REQ-1.6.1's setup wizard — an unrelated MCP-protocol-adjacent term
collision, not the same concept). The closest existing pattern,
`architecture.md` §5's "Version-aware regions" (`// mcpify:versions:begin` /
`:end` marker blocks that `add-version` re-renders via direct string
patching), is explicitly scoped to "a small, pure-data code literal (a
label→file map, or a list of choices)" — nowhere near the shape of a whole
new hand-authored capability spanning 12 new files. This is a genuine
product-scope gap, not a template bug being silently propagated — worth
flagging as a candidate for a new `mcpify/docs/DOC-GAPS.md` entry, or more
fundamentally a roadmap question: should mcpify's generator eventually own
an MCP-prompts capability itself, the way it owns tools, rather than leaving
every generated repo to reinvent the escape hatch by hand?

### Resulting work
`docs/mcp-prompts-workflow-plan.md` was written from scratch to establish
this pattern (file layout, the "agnostic phrasing" rule for
version-drifting `operationId`s, delegation/token-economy design) before any
code was written — a reasonable one-off response, but the underlying gap
(mcpify's own docs don't cover this) will recur for every other
mcpify-generated repo that adds a hand-authored capability.

## 2026-07-19 — v0.5.8 — Windows-specific races and hangs in the store-path and setup-wizard tests (shared mcpify-template gap)

### Doc gap
No doc specified Windows-specific behavior for two generated patterns: (1)
concurrent extraction/rename of the embedded store when a *different OS
process* (not just a different thread) has the destination briefly open,
and (2) `inquire`'s interactive prompts blocking indefinitely on a
non-console stdin on GitHub Actions Windows runners rather than failing
fast the way Unix does.

This entry bundles two distinct root causes, tracked differently:

- **(1), the store-rename race — already tracked.** This is mcpify's own
  `docs/DOC-GAPS.md` "Windows-specific file-locking/timing semantics
  unaddressed for the embedded store" entry, v0.11.1 bullet ("Added retry
  logic around the store-file rename to tolerate a cross-process race
  during store extraction"), landed by mcpify the same day (2026-07-19) as
  this repo's fix.
- **(2), the setup-wizard hang — not yet tracked.** mcpify's matching fix
  (`mcpify` v0.11.1, same release: "Stopped the Rust target's setup-wizard
  smoke test from hanging on GitHub Actions Windows runners") shipped in
  the *same* mcpify release as (1) above, but mcpify's own
  `docs/DOC-GAPS.md` entry for that release only narrates the store-locking
  half — the setup-wizard/interactive-prompt-hang half isn't mentioned
  there at all, even though it's a different root cause (child-process
  stdin/TTY handling on Windows, not file-locking) that happens to share a
  release. See also v0.5.1 below, the first (TTY-requirement, not hang)
  instance of this same broader "generated tests drive interactive prompts
  and nothing documents Windows CI's non-interactive stdin behavior" gap —
  neither instance has a `docs/prd.md`/`architecture.md` root cause on
  record; REQ-2.3.6 ("Testing") requires a generated test suite but never
  addresses headless/non-interactive CI execution for anything that drives
  `inquire`.

### Resulting work
Added a short retry-with-backoff (5 attempts, 50ms × attempt) around the
store rename for the cross-process race, and skipped the `setup` smoke test
specifically on GitHub Actions Windows (via a runtime `cfg!(windows) &&
GITHUB_ACTIONS` check, not a blanket `#[cfg(windows)]`, so a real Windows
developer machine still gets full coverage).

## 2026-07-19 — v0.5.5 / v0.5.6 — generated stdio-transport tests assumed POSIX-only error/EOF behavior (shared mcpify-template gap)

### Doc gap
No doc specified that Windows's stdin/stdio handling differs meaningfully
from POSIX for the generated stdio-transport smoke tests — an
immediately-closed child stdin doesn't surface the same `rmcp` error text on
Windows (0.5.5), and a prior fix unlocking Windows CI to actually reach this
test revealed it could hang outright rather than just report differently
(0.5.6, previously required a ~5-hour manual cancellation).

**Closely related to, but not itemized in, mcpify's own retrospective.**
The matching upstream fixes are `mcpify` v0.10.7 ("Relaxed a stdio-transport
error assertion in generated Rust tests that was too strict/fragile on
Windows") and v0.10.8 ("Stopped the Rust target's stdio-transport smoke test
from hanging on GitHub Actions Windows runners"), both 2026-07-19 — inside
the date range mcpify's "Windows-specific file-locking/timing semantics
unaddressed for the embedded store" entry claims (v0.10.5-v0.11.11), but
that entry's own itemized bullet list jumps straight from v0.10.5 to
v0.11.1 and never names v0.10.7/v0.10.8. That's a real gap in mcpify's own
retrospective: this fix isn't about the embedded *store* at all (it's about
the stdio *transport* smoke test's child-process I/O), so folding it into
the store-focused entry by date-proximity alone would understate the
breadth of "no doc addresses Windows platform semantics" — `architecture.md`
never discusses generated smoke tests' platform-specific process I/O
assumptions at all, store-related or not.

### Resulting work
Relaxed the exact-error-text assertion to Unix-only while keeping the
platform-independent property (handshake never completes, process exits
non-zero) checked everywhere; then skipped the test specifically on GitHub
Actions Windows via a runtime check once the real hang was understood.

## 2026-07-19 — v0.5.3 — store-path caching had no per-process guard against concurrent extraction (shared mcpify-template gap)

### Doc gap
The embedded-store lifecycle doc gap (see Lessons #2) struck again:
`resolve_store_path` re-extracted and renamed the embedded store on *every*
call rather than once per process as its own docstring claimed, and nothing
guarded concurrent access — on Windows, a rename over a destination another
thread already had open could fail outright (not just be non-atomic, as
POSIX allows), surfacing as unrelated MCP-protocol test failures.

**Already tracked — see mcpify's `docs/DOC-GAPS.md` "Windows-specific
file-locking/timing semantics unaddressed for the embedded store" entry,**
whose v0.10.5 bullet ("`fix(rust): eliminate Windows-only race in
resolve_store_path`") is this exact fix, landed by mcpify the same day.
Root cause per that entry: `architecture.md` §2 never mentions concurrency
for `mcp_store.db` extraction/embedding at all.

### Resulting work
Cached the resolved path per API version behind a mutex, so extraction
genuinely happens once per process. Also fixed a related test fixture that
deleted its backing file while still holding an open connection to it — a
pattern POSIX tolerates and Windows does not.

## 2026-07-19 — v0.5.2 — cargo-dist expects its own auto-generated release workflow shape (shared mcpify-template gap, fixed upstream in mcpify)

### Doc gap
No doc specified that `cargo-dist`'s `dist host --steps=create` (invoked by
every real release run) validates the release workflow's shape against its
own auto-generated multi-job template — and fails outright against this
repo's deliberately simplified hand-written workflow, unless told the
divergence is intentional.

**Not yet in mcpify's own retrospective, despite an upstream fix existing.**
`mcpify` shipped the matching fix as v0.10.3 ("Generated Rust projects'
release workflow now allows a dirty git tree by default, matching how the
release actually runs in CI") and a follow-up correction v0.10.4 ("Moved the
`allow-dirty` `cargo-dist` setting to the correct `[dist]` table — it had
incorrectly been placed under `[dist.github-custom-runners]`"), both
2026-07-19, but `mcpify/docs/DOC-GAPS.md` has no entry naming this gap. Root
cause traces to `mcpify/docs/prd.md` REQ-2.3.7 ("Packaging & delivery"),
which requires a CI/CD pipeline "matching the delivery pattern already
proven by both reference servers" but never states that a hand-simplified
workflow diverging from `cargo-dist`'s own expected shape needs an explicit
opt-out flag — worth a fresh mcpify `docs/DOC-GAPS.md` entry, especially
since it took mcpify itself two attempts (v0.10.3 then v0.10.4) to place the
setting correctly.

### Resulting work
Added `allow-dirty` to tell `cargo-dist` the workflow divergence is

thoroughly, at v0.4.0 — the v0.2.3/0.2.4 fix added the `--all` flag but
didn't make it the default or add verification, which is why the same class
of bug reappeared for the 9.4 version specifically a week later.)

**Matching upstream fix exists, but no dedicated `docs/DOC-GAPS.md`
entry.** `mcpify` v0.5.6 (2026-07-06, same day): "Made `VERSION_STORE_FILES`
public, always refresh store extraction, and added an `--all` backfill
option in the Rust target's version-store handling" — this is the same fix.
Root cause, per `architecture.md` §5: multi-version support was added as a
retrofit onto a design that originally assumed exactly one store, and
nothing in that section states that per-version *derived* data (as opposed
to the raw ingested spec) must be regenerated/verified for every version,
not just whichever one happens to be default. See also v0.4.0 above, where
the same class of bug reappeared for a specific version even after this
fix existed — evidence the doc gap is really "nothing verifies a store's
completeness," not just "no `--all` flag existed."

### Resulting work
`populate_embeddings` gained an explicit-path argument and an `--all` flag
to backfill every version the project's ledger knows about (bare invocation
stayed unchanged for the Dockerfile); also added a test asserting every
`VERSION_STORE_FILES` label has a matching `VERSION_STORE_BYTES` entry.
Then ran it across all 30 versions supported at the time, and made the
temp-dir store extraction always overwrite (it previously skipped writing
if a stale file already existed, silently serving outdated data after a
rebuild).

## 2026-07-06 — v0.2.1 / v0.2.2 — embedded-store path resolution didn't account for an installed or relocated binary (shared mcpify-template gap)

### Doc gap
No doc specified how the generated server should locate its bundled
`mcp_store*.db` file across every real invocation context — the initial
implementation only ever looked in the current working directory, which
works for `cargo run` from a checkout but fails the moment the binary is
installed and invoked from elsewhere, or moved/the checkout is deleted.

**Already tracked — see mcpify's `docs/DOC-GAPS.md` entry "2026-08-01 -
filesystem paths must not depend on launch-time CWD (cross-cutting, not yet
released)."** That entry's own "Resulting work" list opens with this exact
sequence: "v0.5.4 (2026-07-06): `fix(rust): generate store db path
resolution with exe-dir fallback`" and "v0.5.5 (2026-07-06): two follow-up
fixes moving from a path-fallback chain to embedded-only store resolution"
— the same two-step fix (exe-dir fallback, then embedded-bytes-only) as
this repo's v0.2.1/v0.2.2, landed by mcpify the same day. Root cause per
that entry: no document — not `prd.md`, not `architecture.md`, not any
`vN-implementation-plan.md` — ever states a blanket constraint that
anything a generated project reads/writes from disk must resolve from an
explicit absolute base rather than the process's CWD. mcpify's own entry
notes this constraint was still unwritten as of 2026-08-01 (after this
repo's own history ends), addressed only in an unreleased, in-progress fix
at that point — i.e. the gap outlived every one of the many downstream
patches it caused, including this repo's.

### Resulting work
Two-step fix: first added an exe-directory fallback (mirroring the
install-dir fallback the config cascade already used), then realized that
was still fragile and instead embedded every version's `.db` bytes directly
into the compiled binary via `include_bytes!`, extracting to the OS temp
dir on first use — removing the filesystem-fallback chain entirely as dead
code, since the embedded copy is always available regardless of invocation
location.

## 2026-07-06 — v0.2.0 — the OpenAPI spec this server was generated from didn't declare Bitbucket's full auth surface (repo-specific)

### Doc gap
No doc (spec-derived or otherwise) captured that Bitbucket Data Center
accepts a bearer-token Personal Access Token in addition to Basic auth — the
OpenAPI spec this server was generated from only declares Basic, so the
generated auth strategy set was incomplete for the real API from the start.
This is a genuine domain gap in the upstream spec, not something the
generator or this repo's own docs could have caught without direct
Bitbucket API knowledge.

This is correctly repo-specific, confirmed by checking mcpify's own scope:
`mcpify/docs/prd.md` REQ-1.2.2 and `mcpify/CHANGELOG.md` v0.1.0 both
confirm the generator's auth-scheme profiling *already* supports
"Bearer-PAT" as one of its five recognized scheme categories
(Basic/API Key/Bearer-PAT/OAuth2/OAuth1-style) from its very first release —
so the generator was never missing PAT support. The gap here is entirely in
the upstream Bitbucket Data Center OpenAPI spec, which simply never
*declared* PAT as an available scheme (REQ-1.2.1's `securitySchemes`
inspection can only emit a strategy for what the spec actually declares).
No mcpify doc could plausibly have caught this without Bitbucket-specific
API knowledge.

### Resulting work
Added a `PatAuthStrategy` alongside the existing `BasicAuthStrategy`, a new
`AuthMethod::Pat` config value, and updated the setup wizard to let a user
choose between the two.

## 2026-07-05 — v0.1.2 — helper binary naming risked a collision (shared mcpify-template gap)

### Doc gap
No doc specified a namespacing convention for the helper binaries a
generated project builds alongside its main CLI (this repo ships
`bitbucket-dc-mcp-populate-embeddings` and `bitbucket-dc-mcp-healthcheck`
today) — the initial implementation didn't namespace one of them, risking a
collision with other binaries on a user's `PATH`.

**Matching upstream fix exists (`mcpify` v0.5.3, 2026-07-05: "Namespaced the
Rust target's generated helper binary to avoid collisions with other
binaries"), landed the same day as this repo's own fix — but no
`docs/DOC-GAPS.md` entry names the gap.** `architecture.md`'s Folder
Structure diagram doesn't mention helper/auxiliary binaries at all (only the
main entry points, `index`/`cli`-equivalent files), so there's no doc-level
statement that every binary a target emits — not just the primary one —
needs a collision-safe name. Minor in isolation (caught in the very first
release, before this repo had real users), but worth folding into a fresh
`docs/DOC-GAPS.md` entry about generated-binary naming conventions if one
gets written for the closely-related README/Folder-Structure gaps above.

### Resulting work
Namespaced the helper binary under the project's own binary-name prefix, in
the very first release, before this repo had any real users — a fix landed
early enough that it's mostly a signal the initial generator output itself
needs this convention baked in, not that it was a live incident.
